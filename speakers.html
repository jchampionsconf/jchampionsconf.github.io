Anton Arhipov

Abstract

Learn how coding agents use IntelliJ IDEA’s debugger and logpoints to inspect runtime behavior without modifying source code, including inside compiled libraries.


When code misbehaves, coding agents often fall back on an old habit. They add print statements. The method works. It also changes the program before the agent understands the problem.
The debugger provides a cleaner way to find the evidence. Logpoints inspect application state while the program keeps running. They can write custom messages without changing the source. You can even place them inside compiled third-party libraries. Every output line links back to the code that produced it. This includes logpoints and regular loggers as well as print statements.
IntelliJ IDEA makes its debugger tools available to coding agents. The debugger skill covers dozens of tools and settings. Few developers keep all of them in their heads. The complete playbook fits into the agent's context.
The agent combines that debugger knowledge with its understanding of the project code. It can choose useful locations for breakpoints and logpoints. It can start a debug run configuration and read actual values. As the evidence develops, it can move its observation points. The source stays untouched.
What attendees will learn:
- How Logpoints capture runtime state without suspending the program or modifying its source
- How to investigate behavior inside compiled third-party libraries
- How navigable debugger output connects runtime observations to their origin in code
- How an agent combines code context with debugger knowledge to place useful breakpoints and logpoints

Session: Teaching a New Dog Old Tricks: Give the Agent a Debugger

Patrick Baumgartner

Abstract

Embabel uses GOAP and strongly typed actions to build explainable, deterministic, testable AI agents within existing Java and Spring applications.


Large Language Models enable powerful new AI capabilities, but production-grade enterprise agents require more than prompting alone. Prompt chaining often results in non-deterministic behavior, limited traceability, and systems that are difficult to control and test. This talk introduces Embabel, an open source agent framework for the JVM created by Rod Johnson, founder of the Spring Framework. Embabel enables controllable, explainable, and production-ready agentic systems directly within existing Java and Spring applications. Rather than orchestrating behavior through prompts, Embabel applies Goal-Oriented Action Planning (GOAP). Agents are composed of strongly typed actions, goals, and domain models, allowing execution paths to be dynamically replanned when assumptions change or steps fail. The result is agent behavior that remains explainable, deterministic, and testable. The talk demonstrates why LLM-driven orchestration often breaks down in enterprise environments and how teams can build robust, maintainable, and controllable AI agents without introducing a new tech stack, relying on fragile prompt logic, or sacrificing architectural control.

Session: Stop Prompting, Start Planning Reliable Agentic AI with Embabel

Johannes Bechberger

Abstract

Explores six low-level uses of native Java agents, including heap dump sanitization, JFR integration, heap watermark reactions, GC control, thread hiding, and interrupt suppression.


Native Java agents are usually used to observe the JVM. With a little HotSpot knowledge, they can also help you solve problems that are difficult or impossible to tackle with the standard Java APIs.
In this talk, we’ll look at six practical and surprising use cases. We’ll show how to sanitize heap dumps before they are written to disk for GDPR compliance, turn JDK log events into JFR events, react to heap watermarks without polling, and disable garbage collection at runtime for controlled benchmarking.
We’ll also explore more unusual applications: hiding Java threads from thread dumps and suppressing asynchronous interruptions such as Thread.interrupt().
Along the way, we’ll look at HotSpot’s internal data structures and classes, and see how we use native hot patching to modify a running JVM. While these techniques are low-level and often version-specific, they can give you powerful new tools for solving JVM problems.

Barry Burd

Abstract

AI-generated code is exposing gaps in developer understanding, requiring stronger education, hiring, code review, debugging, and security standards.


A generation of college students can produce working applications without being able to read what they submitted. The model wrote it, the demo passed, and no one in the room can say why. We’re calling that an education. In a few years, we’ll call them your new hires.
The same dynamic is already loose in enterprise teams. When AI can generate plausible code on demand, developers at every level ship code they can’t fully explain, and the bill comes due later. It’s a review that rubber-stamps what no one understands, a production incident whose own author can’t debug it, a security flaw that passed because it looked right, or a maintenance drag of a codebase no one on the team can actually read. “It works” and “we understand it” are different claims, and the distance between them is where enterprise risk accumulates.
It’s time for a correction. The developer’s job is no longer to type code. It’s to tell working code from merely convincing code, and to know the platform, the framework, and the application domain well enough to see what the model got wrong. A developer or a student who trusts the vibe-coded result has learned nothing durable.
In my current Computer Science course, I teach against that default. Students get real instruction on fundamentals. They work in teams. They’re graded on presentations in which they explain what they created, how they created it, and how it works. If they can’t explain it, they don’t get credit for it. I assess understanding, not output. I’ll show why that same standard belongs in your hiring bar, your code review, and your on-boarding, and how to put it there.

Session: We’re Graduating Developers Who Can’t Read Their Own Code, . . . And Sending Them to Your Company

Eric Deandrea

Abstract

Explore Docling Java, an open-source JVM toolkit for transforming complex documents into structured data and building effective RAG pipelines for AI applications.


We blame the model when AI hallucinates. But the most common cause isn't a flawed model — it's flawed data. Or worse, no meaningful data at all.
A document might look perfect on screen, but underneath it's often a flat stream of characters without structure and headings that are just big bold text, tables reduced to a jumble of disconnected cells, figures with captions that bear no relationship to the image they describe, and footnotes scattered wherever the layout engine decided to put them. The relationships between sections, the hierarchy of content, the intent behind a table, etc is lost. What looks like rich, structured content to a human is, to an AI, little more than an undifferentiated wall of tokens.
Enter Docling, an open-source toolkit that tackles this problem head-on: it converts messy, real-world documents into clean, structured, AI-ready data. It understands page layout, table structure, reading order, formulas, and code blocks, producing a rich unified document representation that downstream AI systems can actually reason over.
The catch? Everything we've described lives in the Python ecosystem. And last time I checked, I'm a Java Champion! Does that mean I'm out of luck? Spoiler - no! That's exactly the gap Docling Java was built to close!
In this session, I'll introduce Docling Java and dive into how it brings first-class document intelligence to the JVM. I'll walk through the library's architecture and show how it plugs naturally into the frameworks and AI stacks you're likely already using.
Along the way, I'll build up from simple to more sophisticated patterns, with a particular focus on building RAG pipelines that produce the kind of meaningful, structured data that gives your model a fighting chance to stop taking the blame. By the end, you'll leave with concrete, runnable patterns you can take back to your own Java codebase.

Kenneth Kousen

Abstract

A practical guide to turning inherited vibe-coded JavaScript and Spring Boot projects into dependable codebases with tests, boundaries, and disciplined refactoring.


Non-developers are shipping working software now. A marketing lead builds an internal tool over a weekend, a founder ships a prototype that gets customers, a researcher writes the script the whole lab depends on. Then the tool has to be dependable, and someone has to make it so. That someone is increasingly going to be you, and the job is not "rewrite it." The job is to move it up a scale without losing what already works.

I think of projects as doghouses, cabins, and skyscrapers. A doghouse is small, casual, and shipped in a weekend, which is the vibe coding sweet spot. A cabin is modest but dependable, with a testable core and explicit boundaries. A skyscraper adds coordination, review gates, and CI discipline because other people have to work inside it. Most inherited vibe-coded projects need to become cabins, and the mistake in both directions is expensive. Build a doghouse like a skyscraper and you never finish. Run a skyscraper like a doghouse and it fails in ways that cost real money.

This session walks the doghouse-to-cabin transition on two real projects using Claude Code. A single-file JavaScript app that a request for tests forces into a testable core with boring DOM glue. A Spring Boot certificate service that started as a joke and ended with property-based tests on its cryptography. Along the way we do the read-only orientation pass that makes the agent mark where it is guessing, write the project memory that stops the next session from re-learning everything, decide what actually needs a test, and catch the failures that come with the territory. Tests the agent rewrote until they passed. A confident architecture map that disagreed with the code. A refactor that quietly changed behavior.

You'll leave with a triage sequence for any inherited agent-written codebase, the prompts that drive each step, a rule for knowing when to stop, and a public repository showing both projects before and after.

Jim Manico

Abstract

A practical workflow for specifying, implementing, testing, and reviewing secure Java web APIs with AI coding agents.


AI coding assistants can generate a working feature quickly, but working code is not necessarily secure code. When authorization rules, trust boundaries, and data handling requirements are missing from the context, the model must fill in the gaps. Those assumptions can become production vulnerabilities.

Spec-driven development makes the intended security behavior explicit before implementation begins. In this session, Jim Manico demonstrates how to turn product requirements, threat models, OWASP ASVS requirements, and secure coding guidance into specifications that AI coding agents can use and developers can verify.

Using a Java web API example, we will follow a feature from requirements and architecture through AI-assisted implementation, security testing, and review. We will specify object-level authorization, input validation, safe database access, secrets handling, and security logging, including negative requirements that define what the application must never allow. We will then translate those requirements into acceptance criteria and tests that exercise both legitimate use and abuse cases.

The session also explains where instructions stop and enforcement begins. Repository guidance and reusable security prompts provide context; sandboxing, least-privilege tool access, automated checks, and CI gates provide additional controls. We will examine how human review and independent verification help detect implementation errors, incomplete specifications, and tests that merely repeat the coding agent's assumptions.

Attendees will learn how to:

• Write security specifications with explicit trust boundaries, authorization rules, and testable acceptance criteria.

• Give AI coding agents focused, relevant security context for a Java application.

• Derive positive and negative security tests from requirements and threat scenarios.

• Combine code review, security analysis, and CI checks to verify generated code against the specification.

This practical session is intended for developers, architects, and application security engineers. Familiarity with Java and web APIs is helpful; prior experience with spec-driven development is not required. The workflow applies across AI coding tools and does not depend on a particular model or vendor.

Kito Mann

Abstract

A deep dive into Jakarta Validation, covering custom constraints, enterprise APIs, AI-generated inputs, CLI applications, and reliable validation workflows.


Whether input comes from a user, an agent, or another system, it must be validated. Hand-rolled validation is easy to write, but it's often incomplete and inconsistent across apps. As agents generate more and more code, getting validation right matters more than ever.

Jakarta Validation (formerly Bean Validation) is Java's standard for declarative validation. It has been battle-tested since 2009 and is built into Jakarta EE, Spring, Quarkus, Helidon, and Micronaut. You annotate fields, records, method parameters, return values, and even collection elements with constraints like @NotBlank or @Size, and Jakarta Validation verifies entire object graphs and produces localized, parameterized error messages.

It's a staple for REST and GraphQL endpoints and for entities stored with Jakarta Persistence, Jakarta Data, or Spring Data. But it's just as useful in AI-enabled apps: validating MCP tool arguments and structured LLM output with Spring AI, Quarkus LangChain4j, or OmniHai, then feeding violations back to the model. It even works for command-line apps built with Spring Shell or Picocli.

In this session, we'll dive deep into Jakarta Validation: writing custom constraints, using it in AI-enabled and CLI apps, and making sure your coding agent uses it effectively.

Melissa McKay

Abstract

Learn to diagnose Java memory inefficiencies, reduce JVM heap usage, improve throughput and p99 latency, and lower infrastructure costs through practical code changes.


Suffering from high p99s or other performance issues? If you're like other developers you're pointing your finger squarely at the database access or garbage collector. Yet, our research shows that nearly 60% of Java applications suffer from severe memory inefficiency—bloating their heaps by constantly snacking on empty calories.

The performance penalty for an overfed JVM can be sluggish throughput and it most certainly can be responsible for high p99s. The consequence is inflated cloud costs. The good news? Putting your application on a diet can reduce your JVM's hunger for memory. That can come with outsized improvements in throughput and a tightening of p99 scores. Applying (often relatively simple) code changes that address memory inefficiencies can drastically cut infrastructure costs.

This session acts as your manual for JVM weight management. You will learn how to identify if your app belongs to the infamous "60% club," diagnose the primary culprits driving up your footprint, and apply practical coding techniques to slim down your heap.

Session: A Java Developers Guide on how to bloat your JVM

Bazlur Rahman

Abstract

Live coding with JDK 25 explores virtual-thread bottlenecks, queue control, lock contention, and why timeouts, cancellation, and cleanup do not guarantee stopped work.


Virtual threads make it easier to handle many requests at once. But what happens when those requests all need the same few database connections, wait for the same lock, or keep running after a timeout?

In this live-coding session, we’ll start with a brief introduction to virtual threads, then work through three before-and-after experiments on plain JDK 25. We’ll watch requests pile up behind a busy dependency, see a shared lock force concurrent tasks to run one at a time, and discover why a caller giving up does not mean its task has stopped.

For each problem, we’ll make an explicit design decision: reject excess requests before they join a growing queue, keep independent slow operations outside locks, and connect timeouts to cancellation and cleanup. We’ll examine what each change improves and what it cannot guarantee, including why requesting cancellation is not the same as confirming that work has stopped.

Session: You Enabled Virtual Threads. Now What Breaks?

Glenn Renfro

Abstract

AI-generated code is exposing gaps in developer understanding, requiring stronger education, hiring, code review, debugging, and security standards.


A generation of college students can produce working applications without being able to read what they submitted. The model wrote it, the demo passed, and no one in the room can say why. We’re calling that an education. In a few years, we’ll call them your new hires.

The same dynamic is already loose in enterprise teams. When AI can generate plausible code on demand, developers at every level ship code they can’t fully explain, and the bill comes due later. It’s a review that rubber-stamps what no one understands, a production incident whose own author can’t debug it, a security flaw that passed because it looked right, or a maintenance drag of a codebase no one on the team can actually read. “It works” and “we understand it” are different claims, and the distance between them is where enterprise risk accumulates.

It’s time for a correction. The developer’s job is no longer to type code. It’s to tell working code from merely convincing code, and to know the platform, the framework, and the application domain well enough to see what the model got wrong. A developer or a student who trusts the vibe-coded result has learned nothing durable.

In my current Computer Science course, I teach against that default. Students get real instruction on fundamentals. They work in teams. They’re graded on presentations in which they explain what they created, how they created it, and how it works. If they can’t explain it, they don’t get credit for it. I assess understanding, not output. I’ll show why that same standard belongs in your hiring bar, your code review, and your on-boarding, and how to put it there.

Session: We’re Graduating Developers Who Can’t Read Their Own Code, . . . And Sending Them to Your Company

Abstract

Demonstrates how Java's Vector API accelerates matrix multiplications in the Strange quantum computer simulator across JIT and hardware configurations.



The Vector API is still in the incubation phase, but some of its capabilities are ready to use. Its SIMD capabilities allow hardware vector registers to be used more efficiently, leading to hardware-accelerated performance in arithmetic computations, e.g. matrix multiplications.

Matrix multiplications are heavily used in Quantum Computer simulators. In this session, we will show how using the Vector API drastically improves the performance of Strange, which is a Quantum Computer simulator written in Java (see https://github.com/redfx-quantum/strange).

Suggested agenda:
* light-weight intro/explanation of the basic concepts of Quantum Computing
* introduce Quantum Computer simulators, and their dependency on matrix multiplications
* show existing code
* briefly introduce the Vector API
* replace existing code with Vector-API based code
* show performance gains for different situations (e.g. before/after JIT kicks in, and on different systems with different register sizes)
* key takeaways
